# UMI 박스 적재 데이터의 IGRIS-C WALK_LOW 재생

`rcvsungmincho/Box_palletizing_UMI_macos_intern_merged`의 에피소드를 IGRIS-C가 시뮬레이션에서 따라 한다.
하체는 제조사 WALK_LOW가 서 있게 두고, 허리 3축 + 양팔 14축만 SDK LowCmd로 움직이며 재생 중에 IK를 푼다.

```text
에피소드(15 Hz, pelvis 기준 손바닥 포즈)
  → retarget: 손바닥 → 로봇 EE, 든 구간은 양손을 한 쌍으로
  → 100 Hz 목표 → IK(허리 3 + 팔 14) → SDK LowCmd (PJS, 100 Hz)
  → 제조사 bridge_sim → controller(WALK_LOW) → 제조사 MuJoCo 3.2.7 (로봇 + 장면)
  → 관측기 body pose → Isaac Sim 렌더
```

물리는 제조사 MuJoCo가 계산하고 Isaac Sim은 장면 제작과 렌더를 맡는다(2026-11-23 사용자 선택).
컨테이너는 `--network none`, private IPC로 뜨며 실기 DDS와 연결되지 않는다. **실기는 한 번도 움직이지 않았다.**

설계와 근거: [DESIGN.md](DESIGN.md).

## 실행

저장소 루트에서 실행한다. 필요한 것: `env_isaaclab`(pxr, Isaac Sim 6.0.1), Docker 이미지 `igris-sim:jazzy`,
`igris/ws/install`, 데이터셋 로컬 사본, UR5e 책상 장면(`real2sim/ur5e_desk/` 또는
`.local/real2sim_ur5e_desk_f976624/` — `origin/real2sim/ur5e-desk-scene` 브랜치에서 풀어 둔 것).

```bash
export PYTHONPATH=$PWD
OUT=$PWD/outputs/umi_walklow_replay_$(date +%Y%m%d_%H%M%S)
env_isaaclab/bin/python -m igris.umi_walklow_replay.run all --out $OUT \
  --dataset /DATA/ykkim/datasets/Box_palletizing_UMI_macos_intern_merged --episode 0
```

`all`은 아래 단계를 차례로 실행한다. 단계별로 따로 실행할 수도 있다(같은 `--out`).

| 단계 | 하는 일 | 결과 |
|---|---|---|
| `prepare` | 에피소드 추출, 목표 생성, 장면 USD, 손 자세를 넣은 제조사 모델, 장면 합성 | `episode/`, `targets.npz`, `scene/`, `model/`, `run/` |
| `labels` | (`all`에서는 `--stream`을 줄 때만) 목표를 로봇이 제 시계로 따라갈 수 있는 포즈 라벨과 그 스트림으로 바꿈 | `labels.npz`, `stream.npz`, `labels.json` |
| `start` | 제조사 libmujoco로 로봇 파라미터 동일성 검사 후 격리 컨테이너 기동 | `run/model.json`, `run/runtime.json` |
| `bringup` | reset → torque on → HOME → WALK_LOW (상체는 유지 발행기가 잡음) | `BRINGUP … pelvis …` |
| `replay` | 컨테이너 안에서 IK + LowCmd 재생 | `run/replay_log.npz`, `run/replay_result.json` |
| `stop` | 이 실행의 컨테이너만 정지 | |
| `analyze` | 추종·균형·박스별 결과 | `run/analysis.json` |
| `render` | 기록된 물리 상태를 Isaac Sim으로 3구도 영상 렌더 | `run/render/<카메라>/recording.mp4` |

출력 폴더는 매번 새로 만든다. 저장소 밖(`/DATA/ykkim/outputs/umi_walklow_replay/...`)을 `--out`으로 줘도 된다
(2026-11-23부터 새 출력은 `/DATA`에 둔다). 이미 쓴 폴더로는 `prepare`·`start`·`replay`가 거부된다.
에피소드 재생은 시계대로면 약 75초(실시간의 0.93~0.98배), 기본인 속도 제한에서는 1.3~2배 길다. 렌더는 15 fps 3구도 기준 약 17분이다(2026-11-24부터의 화질 설정; 이전 설정은 10 fps에서 약 6분).

주요 옵션: `--episode N`, `--speed`(1보다 작으면 느리게), `--squeeze`(손바닥이 박스 면을 누르는 양),
`--shift DX DY`(로봇이 서는 위치), `--carton-height`(롤테이너 적재면 높이), `--case-top`(케이스 윗면 높이),
`--cart-setback DX DY`(롤테이너 위치), `--raw-hands`(기록 손 프레임 보정 끄기, 아래 절 참고),
`--joint-speed`·`--joint-acceleration`(관절 속도·가속도 제한, 0이면 시계대로 재생), `--anchor {pelvis,support,feet,none}`,
`--no-reach-hold`·`--hold-lean START FULL`·`--rate-floor`(아래 "숙임 → 골반 후퇴 되먹임 차단" 절),
`--limit-seconds`(앞부분만 재생), `--gains FILE`(허리·팔 LowCmd Kp/Kd 프로파일 교체, 아래 "서 있을 때의 흔들림" 절), `--elbow-prior`(HL-IK 팔꿈치 prior 켜기, 아래 절 참고),
`--checkpoint`(다른 FiSTA 체크포인트), `--raw-tracking`(기록 tracking 보정 끄기, 아래 절 참고), `--toe-in DEG`·`--rebase-waist`·`--toe-free LOW HIGH`·`--pad {flat,capsule}`
(재타깃 시험, 아래 절 참고), `--ik {mink,numpy}`·`--no-teleop-posture`·`--full-orientation`("현재 기본 설정" 절 참고),
`--fps`·`--render-subframes`·`--render-name`·`--camera NAME`(영상 렌더, 아래 "렌더 화질" 절; `--camera UmiFront`처럼 주면 그 구도만),
`--no-slack-compensation`·`--support-clearance M`(아래 "1층 박스에서 손이 케이스에 닿는 문제" 절),
`--heading-hold`(아래 "보행 모듈의 heading 모드" 절, 기본 끔),
`--elbow-prior teleop`·`--elbow-prior swivel`(아래 "텔레옵으로 다시 학습한 FiSTA 팔꿈치 prior" 절, 기본 끔),
`--stream [FILE]`·`--stream-hz`·`--stream-latency`·`--slack {measured,calibrated}`(아래 "포즈만 받는 실시간 실행" 절, 기본 끔).
정책이 목표를 내는 폐루프 실행(`worker.py --policy`, `--waist`)과 A100용 `container_run.py`는 "로봇 카메라 시뮬 데이터와 상대 EE ACT" 절에 있다.

## HL-IK 팔꿈치 prior (선택 기능, `--elbow-prior`)

재생 영상의 팔 자세가 어색하다는 지적에 따라 `igris/hl_ik`의 FiSTA 팔꿈치 prior를 IK에 연결했다(2026-11-23).
**기본값은 꺼져 있다.** 켜면 팔꿈치는 조금 더 바깥으로 벌어지지만 이 시뮬에서 적재 성공률이 떨어진다.
이 절의 수치는 numpy IK(`--ik numpy`)에서 사람 동작으로 학습된 체크포인트로 잰 것이다. 2026-11-24부터 `--elbow-prior`는
기본 IK인 mink에서도 동작하고(QP의 팔 자세 항으로 들어감), 텔레옵으로 다시 학습한 체크포인트는 `--elbow-prior teleop`이다
(아래 "텔레옵으로 다시 학습한 FiSTA 팔꿈치 prior" 절).

- 체크포인트: `outputs/hl_ik_20260915/training/full/seed_42/best.pt`(4090에서 복사, sha256 일치).
  컨테이너에 torch가 없어 `prepare`가 `model/fista.npz`로 내보내고 워커는 numpy로 평가한다(torch와 2e-5 이내 일치).
- 손 포즈가 1순위다. 손 6자유도를 뺀 팔의 남은 1자유도(스위블)만 예측 팔꿈치 쪽으로 돌린다.
  손 정확도는 그대로다(오프라인 IK 잔차 p99 1 mm 미만).
- 스위블이 prior를 따르지 않는 곳: 팔 관절이 한계 0.10 rad 안쪽일 때, 위팔·팔꿈치 쪽 전완이 박스 표면 8 cm
  안쪽일 때(박스 자세는 시뮬 실측). 그 안에서는 벗어나는 방향으로 돈다.

에피소드 0 결과(시뮬레이션, 마지막 자세 기준 3단 쌓임):

| 구성 | 쌓임 | 스위블 평균 왼/오 | 오른 팔꿈치가 어깨선 안쪽인 시간 |
|---|---|---|---|
| prior 없음(기본) | 17 / 18 | 30~33° / 7~11° | 64~68% |
| prior, 처음 구현(일반 영공간 과제) | 2 / 3 | 44~53° / 9~16° | 51~65% |
| prior, 스위블 전용 | 7 / 10 | 37~56° / 9~47° | 34~64% |
| + 박스 간섭 회피 | 4 / 6 | 43~57° / 15~40° | 43~55% |
| + 관절 한계 회피(현재 `--elbow-prior`) | 5 / 9 | 47~66° / 28~48° | 37~61% |
| + 예측 팔꿈치 높이를 학습 범위로 제한(폐기) | 1 / 6 | | |

prior 없음 18회는 prior 작업 전 9회와 같은 날 prior 실행과 섞어 돌린 9회를 합친 것이다(이후 2회를 더해 지금은 18/20). 구성별 횟수가 적어
prior 구성끼리의 차이는 판단할 수 없고, "prior를 켜면 덜 쌓인다"(전체 18/28 대 17/18)만 읽을 수 있다.
영상: prior 없음 `outputs/umi_walklow_replay_20261123_143619_ep0_final`, prior 사용
`outputs/umi_walklow_replay_20261123_160019_gd_e`(각각 `run/render/<카메라>/recording.mp4`).

스위블은 어깨–손 축 둘레의 팔꿈치 각도로 0°가 바로 아래, +가 바깥이다. `analysis.json`의 `arm_posture`에 실행마다 기록된다.
시뮬 없는 IK만으로는(`python -m igris.umi_walklow_replay.offline`) 스위블 평균이 32°/10° → 45°/36°,
오른 팔꿈치가 어깨선 안쪽인 시간이 39% → 8%로 바뀐다.

알게 된 것:

- 손 포즈를 지키는 한 바꿀 수 있는 것은 스위블 하나뿐이라 영상에서의 차이는 작다. 이 데이터의 손 포즈는 FiSTA 학습
  분포의 가장자리다(손 위치 약 2σ, 방향 2.5~3.5σ). 어색함의 원인은 아래 "텔레옵 관절 데이터와의 비교" 절에서 따로 확인했다.
- prior는 시작 자세와 무관하게 10초 안에 같은 팔꿈치 궤적으로 수렴한다(연결 자체는 정상).
- 실패 방식은 세 가지였다. (1) 일반 영공간 과제로 넣으면 손을 고정하려고 허리 yaw가 대신 돈다(준비 자세에서 24°)
  → 스위블 전용으로 바꿈. (2) 벌어진 오른 위팔이 대기 중인 박스에 4~8 cm까지 접근해 넘어뜨림 → 간섭 회피.
  (3) 팔꿈치가 벌어지고 올라간 자세(실패 실행에서 어깨보다 11 cm 위)에서 허리가 기울고 보행 제어기가 골반을
  12 cm 넘게 옮겨 첫 박스를 놓다가 넘어뜨림 → 관절 한계 회피로는 없어지지 않았다. 이것이 기본값을 끈 이유다.

## 텔레옵 관절 데이터와의 비교 (2026-11-23)

로봇 관절로 기록된 `kimyg119/Igris_Teleop_Box_Palletizing`(834 에피소드, 15 Hz)을 기준으로 실행 경로를 검증했다.
허리·다리·목까지 있는 31축은 `full-signals-15hz` 태그에만 있다(기본 판은 양팔 14축). 로컬 사본은
`/DATA/ykkim/datasets/Igris_Teleop_Box_Palletizing_full_signals_15hz`. 텔레옵은 WALK_LOW로 선 채 허리 yaw를
약 ±1 rad 쓰고 roll·pitch는 거의 쓰지 않았다.

```bash
OUT=/DATA/ykkim/outputs/umi_walklow_replay/teleop_$(date +%Y%m%d_%H%M%S)
env_isaaclab/bin/python -m igris.umi_walklow_replay.teleop prepare --out $OUT --episode 744 \
  --teleop-root /DATA/ykkim/datasets/Igris_Teleop_Box_Palletizing_full_signals_15hz \
  --scene-dataset /DATA/ykkim/datasets/Box_palletizing_UMI_macos_intern_merged
env_isaaclab/bin/python -m igris.umi_walklow_replay.run start --out $OUT
env_isaaclab/bin/python -m igris.umi_walklow_replay.run bringup --out $OUT
env_isaaclab/bin/python -m igris.umi_walklow_replay.teleop replay --out $OUT            # 기록 관절 그대로
#   ... teleop replay --out $OUT --end-effectors                                      # 같은 동작의 손 포즈를 IK로
env_isaaclab/bin/python -m igris.umi_walklow_replay.run stop --out $OUT
env_isaaclab/bin/python -m igris.umi_walklow_replay.teleop analyze --out $OUT
```

실제 박스 위치가 기록에 없어 장면 물체는 세우지 않는다(추종·균형·자세만 본다).

**1. 실행 경로는 문제없다** (에피소드 744, 43초, 시뮬레이션)

| | 관절 재생 | 손 포즈 → IK 재생 |
|---|---|---|
| 워커 완료, WALK_LOW 유지 | 예 | 예 |
| LowCmd 주기 / 실시간 비율 | 100 Hz / 1.00 | 100 Hz / 1.00 |
| 관절 추종 오차 RMS / 최대 | 0.004 / 0.020 rad | 0.004 / 0.026 rad |
| 손 위치 오차(기록 대비, 시뮬 실측) 평균 / 최대 | 5 / 13 mm | 6 / 16 mm |
| 골반 수평 이동 범위, 최대 기울기 | 3~8 cm, 5.5° | 5~6 cm, 4.9° |
| IK 해와 기록 관절의 차이 | | RMS 0.065 rad, 팔꿈치 평균 1.3~1.5 cm(최대 4.3 cm), 관절 한계 접촉 0% |

로봇이 실제로 낼 수 있는 손 포즈가 들어오면 IK는 기록과 거의 같은 팔 자세를 내고 추종·균형도 안정적이다.

**2. 문제는 UMI 손 목표 쪽에 있다** (텔레옵 "place" 에피소드 40개 대 UMI 재생 7회)

| | 텔레옵(로봇 기록) | UMI 재생 |
|---|---|---|
| 손이 어깨보다 높은 시간 | 78% | 71% |
| 팔 관절이 한계에 닿은 시간 | 0% | 32% (시뮬 없는 IK는 9%) |
| 팔꿈치가 어깨선 안쪽 / 어깨보다 위 | 7% / 0% | 36% / 20% |
| 스위블 p05~p95 | 5~37° | −5~91° |
| 어깨–손 거리 / 팔 길이(0.648 m) 중앙값 | 0.77 | 0.86 (시뮬에서는 0.88) |
| 어깨 roll이 안쪽 한계 3° 이내인 시간 | 0% | 8% (시뮬에서는 21~25%) |
| 팔 관절 속도 중앙값 / p99 | 0.05 / 0.62 rad/s | 0.37 / 2.0 rad/s(속도 한계) |
| 손 속도 중앙값 / p99 | 0.01 / 0.31 m/s | 0.09 / 0.51 m/s |

- 앞서 "손이 어깨보다 높은 것이 주원인"이라고 본 것은 틀렸다. 텔레옵에서도 손은 78%의 시간 동안 어깨보다 높다.
- 실제 차이는 (1) 사람 속도 그대로라 관절 속도가 한계에 닿는 것, (2) 손이 어깨에서 더 멀어 팔이 펴지는 것,
  (3) 그 위치·방향 조합에서 어깨 roll이 안쪽 한계에 붙어 팔꿈치가 몸 안쪽으로 접히는 것이다.
- UMI 에피소드를 절반 속도로 재생하면 3/3회 쌓이고 3/3회 기록 위치에 놓였지만(기본 속도는 17/18, 12/18)
  관절 한계 접촉은 줄지 않았다(45~57%). 속도는 놓는 정확도에, 한계 접촉은 손 목표의 위치·방향에 달려 있다.

**3. cuRobo로 바꾸면 나아지는가** (`igris/igris_curobo`, 4090에서 같은 손 목표를 100 Hz로 풀어 비교, 시뮬 없음)

| | numpy IK(이 패키지) | cuRobo `UpperBodyIK`(3 keypoint) | cuRobo `TorsoArmIK` + 허리 yaw |
|---|---|---|---|
| 텔레옵 744: 손 위치 오차 p50 / p99 / 최대 | 0 / 0 / 0 mm | 4.7 / 35 / 37 mm | 4.8 / 48 / 50 mm |
| 텔레옵 744: 기록 대비 팔꿈치 평균(최대) | 1.5 (4.3) cm | 2.6~5.5 (26) cm | 1.1~2.8 (5.9) cm |
| 텔레옵 744: 성공 판정 / 자기충돌 표시 | | 48% / 100 프레임 | 65% / 259 프레임 |
| UMI 0: 손 위치 오차 p50 / p99 / 최대 | 0 / 1 / 12 mm | 6 / 37 / 67 mm | 6 / 67 / 83 mm |
| UMI 0: 팔 관절 한계 접촉 | 9% | 2% | 2% |
| 한 번 푸는 시간 | 3~4 ms (CPU) | 20 ms | 19 ms |

- 설정: `control_dt_s=0.01`, 속도 한계 팔 2.0 / 허리 1.2 rad/s, `recovery_after_frames=0`, 나머지는 패키지 기본값.
  cuRobo 쪽 가중치는 조정하지 않았다. 푸는 시간은 다른 작업이 GPU를 쓰는 중에 잰 값이다(패키지 문서는 단독 p95 8.4 ms).
- 손 추종 정확도와 기록 자세 재현은 numpy IK가 낫다. cuRobo는 rest·충돌·한계 비용과 손 오차를 함께 최소화하므로
  손이 수 mm~수 cm 물러난다. 손바닥으로 박스를 22 mm 눌러 잡는 이 과제에는 큰 값이다.
- cuRobo 쪽에만 있는 것: 자기충돌 검사, 다seed 전역 해, 그리고 정책의 포즈 chunk를 속도 0.5 rad/s·가속도 2 rad/s²
  이내 궤적으로 바꾸는 `ActionChunkIK`(`igris_curobo/src/igris_ik/robot/action_chunk.py`, 이번에 실행해 보지는 않았다).
- 따라서 IK를 통째로 바꾸는 것보다, 지금 IK에 (a) chunk 단위 속도·가속도 제한과 (b) 자기충돌 검사를 더하는 편이 맞다.
  어느 IK를 쓰든 2번의 원인(손 목표의 속도·거리·방향)은 그대로 남는다.

## UMI 재타깃 시험 (2026-11-23)

위 비교에서 나온 차이를 줄이는 방법을 시험했다. 모두 선택 옵션이며 기본 동작은 그대로다.

몸통 좌표계에서 다시 보니 차이는 두 가지로 좁혀졌다.

| 몸통 기준 | 텔레옵 | UMI 재생 |
|---|---|---|
| 양손 중점의 방위(+가 왼쪽), p05 / 중앙값 / p95 | −7° / 0° / 5° | −5° / 6° / 29° |
| 손끝 방향 중앙값, 왼손 / 오른손(+가 왼쪽) | −17° / 26° (안쪽으로 모음) | −2° / −2° (평행) |
| 어깨 roll 바깥쪽 중앙값, 왼 / 오 | 0.25 / 0.16 rad | 0.24 / −0.03 rad |

- **몸통이 손을 향하지 않는다.** 시뮬에서 골반이 돌면 손 목표는 방에 고정되도록 돌려 주는데 허리 yaw 기준은 돌려 주지
  않았다(이 패키지의 누락). 시뮬 없는 IK에서 골반을 25° 돌려 재현하면 팔 관절 한계 접촉이 9% → 30%가 되고,
  기준도 같이 돌리면 다시 낮아진다. → `--rebase-waist`.
- **손바닥이 완전히 평행하다.** 텔레옵 로봇은 손끝을 17~26° 안쪽으로 모아 박스를 잡는다. 평행하게 두면 어깨 폭(0.34 m)보다
  좁은 박스에서 전완도 평행해야 해서 팔꿈치가 접히고 어깨 roll이 안쪽 한계에 붙는다. → `--toe-in DEG`
  (손을 손바닥 접촉점 둘레로 돌린다. 접촉 평판은 같은 각만큼 되돌려 박스 면에 그대로 평행하게 닿는다 —
  손가락 면이 순응한다고 가정한 것이며 실제 손의 순응은 모델에 없다).

`head.yaw`: UMI의 `state`/`action` 15번째 값이다(yaw만 있음). 양손 중점 방위와 상관 0.995, 크기는 1.11~1.15배,
손보다 0.2~0.33초 먼저 돌고, 범위 −45°~+92°로 허리 yaw 한계(±88°)를 넘는다.

시뮬 없는 IK 비교(에피소드 0 / 5 / 10):

| | 팔 관절 한계 접촉 | 손 오차 p99 | 팔 속도 한계 시간 |
|---|---|---|---|
| 현재(허리를 IK에서 함께 풂) | 9 / 14 / 15% | 1 / 3 / 18 mm | 2 / 5 / 10% |
| 허리 yaw = `head.yaw` 직접 명령, 숙임 허용 | 22 / 30 / 34% | 7 / 20 / 31 mm | 12 / 17 / 16% |
| 허리 yaw만 직접, 숙임 없음(리프트 + 양팔 방식) | 33 / 32 / 36% | 12 / 16 / 18 mm | 20 / 23 / 26% |
| 현재 + toe-in 12° | 4 / 8 / 15% | 1 / 3 / 21 mm | 3 / 5 / 10% |
| 로봇을 놓는 쪽으로 20° 돌려 세움 | 19% (에피소드 0) | 1 mm | 3% |

- 허리를 따로 명령하는 방식은 이 데이터에서는 나빴다. 사람 머리는 손보다 먼저, 더 많이 돌아서 몸통이 손 밑에서 먼저 돌고
  팔이 반대로 감아야 한다. 숙임을 막으면 가장 낮은 박스에 손이 닿지 않는다(최대 오차 28~35 mm).
  텔레옵에서 이 방식이 통한 것은 조작자가 닿는 손 포즈를 골랐기 때문이다.
- 로봇이 서는 방향을 바꾸는 것도 도움이 되지 않았다.

시뮬레이션 결과:

| 에피소드 0 | 쌓임 | 기록 위치 | 팔 관절 한계 접촉 | 오른 어깨 roll 한계 | 오른 팔꿈치 어깨선 안쪽 |
|---|---|---|---|---|---|
| 기본 | 18 / 20 | 13 / 20 | 27~33% | 21~25% | 64~68% |
| `--rebase-waist` | 2 / 2 | 0 / 2 | 22~23% | 17% | 65~70% |
| `--toe-in 12 --rebase-waist` | 6 / 6 | 5 / 6 | 9~35% | 5~22% | 43~58% |

다른 에피소드(2, 5, 10, 20, 25, 30, 각 1회)에서는 고르지 않았다. 쌓임은 기본 3/6(2, 5, 10) 대 재타깃 3/6(2, 5, 25)이고,
한계 접촉은 25번(64% → 7%)과 20번(61% → 50%)에서 줄고 10번(42% → 54%)과 30번(29% → 38%)에서 늘었다.
늘어난 곳은 왼 손목 yaw가 한계에 붙은 경우다(toe-in이 손목 yaw를 쓴다). 좌우 같은 각을 고정으로 주는 방식은
아직 기본값으로 삼을 수 없다.

### 가변 toe-in (IK가 각도를 고름)

고정 각 대신 IK가 손끝 모음 각을 0~25° 안에서 고르게 했다(`--toe-free 0 25`, 선호 각 12°). IK는 손바닥 위 한 점의 위치와
나머지 두 회전만 지키고, 남는 회전은 팔 관절을 한계에서 멀리 두는 데 쓴다. 각도가 변해도 닿도록 접촉면을 둘로 시험했다:
기존 평판(선호 각에 맞춰 돌려 둠)과 손바닥 폭 방향 캡슐(`--pad capsule`, 어느 각에서도 같은 선 접촉).

시뮬 없는 IK(에피소드 0, 2, 5, 10, 20, 25, 30):

| | 팔 관절 한계 접촉 | 오른 팔꿈치 어깨선 안쪽 | 허리 숙임 사용 |
|---|---|---|---|
| 평행(기본) | 9 / 13 / 14 / 15 / 11 / 3 / 10% | 39 / 49 / 45 / 35 / 29 / 7 / 18% | 23 / 27 / 31 / 32 / 27 / 22 / 30% |
| 고정 12° | 4 / 7 / 8 / 15 / 10 / 2 / 8% | 19 / 27 / 21 / 21 / 13 / 0 / 9% | 18 / 22 / 26 / 27 / 24 / 14 / 23% |
| 가변 0~25° | 4 / 7 / 8 / 12 / 9 / 2 / 8% | 0 / 5 / 0 / 2 / 2 / 0 / 2% | 11 / 19 / 23 / 20 / 13 / 5 / 17% |

IK가 고른 각은 대부분 12° 근처(p05~p95 약 9~14°)이고, 일부 에피소드에서 왼손이 0~7°까지 내려간다.
자세 지표는 가변 쪽이 가장 좋다. 남는 한계 접촉은 대부분 왼 손목 yaw(4~11%)이며 toe-in으로는 없어지지 않는다.

시뮬레이션(에피소드 0, 모두 `--rebase-waist`):

| 구성 | 쌓임 | 기록 위치 |
|---|---|---|
| 고정 12°, 평판 = `--toe-in 12` | 6 / 6 | 5 / 6 |
| 가변(항상), 평판 | 0 / 2 | 0 / 2 |
| 가변(든 동안은 12°로 고정), 평판 = `--toe-free 0 25` | 1 / 4 | 1 / 4 |
| 가변(항상), 캡슐 = `--toe-free 0 25 --pad capsule` | 2 / 3 | 2 / 3 |
| 평행, 캡슐 = `--pad capsule` | 2 / 3 | 1 / 3 |

- 쌓인 실행에서는 자세가 더 좋았다(팔 관절 한계 접촉 8~14%, 오른 팔꿈치 어깨선 안쪽 20~36%; 고정 12°는 9~18%, 43~53%).
- 그러나 적재는 고정 12°보다 분명히 못하다. 평판은 각도가 변하면 박스 면에서 들뜨고, 든 동안만 고정해도 접근·이탈 때
  각이 변해 박스를 건드린다. 캡슐은 각에 무관하지만 평판보다 잡는 힘이 약하다(평행 상태로도 2/3).
- 에피소드 10, 30(든 동안 고정, 평판)도 쌓지 못했다.
- 따라서 지금 접촉 모델에서는 가변 toe-in을 쓸 수 없다. 실제 손의 순응(MCP·DIP)을 모델에 넣기 전에는 고정 각이 낫다.

## mink IK와 자기충돌 제약 (`--ik mink`, 2026-11-23)

실행기 보강의 첫 단계로, 직접 구현을 늘리는 대신 mink(MuJoCo 기반 QP 미분 IK)를 두 번째 IK로 넣었다.
`mink_ik.py`의 `MinkIK`는 `ik.IK`와 같은 인터페이스이고, 관절 범위·관절 속도·제조사 결합 한계·자기충돌 간격이
한 QP의 부등식 제약으로 들어간다. 아래 비교를 거쳐 mink가 기본 IK가 됐다(이 절의 수치는 그 전에 잰 것이다).

- 자기충돌 모델: `igris/igris_curobo`의 로봇 충돌 구 3,666개와 검사·무시 쌍을 그대로 쓴다(`collision.py`, numpy).
  링크 좌표계가 제조사 모델과 일치한다. 텔레옵 실측 자세 9,005개에서 겹침 0.01%(양손이 맞닿은 2개), 최소 간격 4 mm로
  오탐이 없다. 간격 4 cm 아래만 정밀 계산해 한 번에 약 2 ms다.
- 제약: 가까운 링크 쌍마다 구 16쌍의 간격이 2 mm 아래로 줄지 않게 한다. 한 쌍만 제약하면 이웃 구가 대신 파고들어
  겹침이 4 cm까지 커졌다(테스트로 발견). 모든 제약은 "정지"를 허용하므로 QP는 항상 풀린다.
- 설치: 시뮬 이미지에는 mink가 없어 Python 3.12용 패키지를 폴더에 받아 읽기 전용으로 붙인다(`UMI_MINK_PY`로 위치 변경).

  mink==1.3.0 qpsolvers==4.13.0 daqp scipy==1.13.1 typing_extensions mujoco==3.11.0      # 컨테이너용 (numpy 1.26)
env_isaaclab/bin/python -m pip install --no-deps --target /DATA/ykkim/vendor_py/mink_host \
  mink==1.3.0 qpsolvers==4.13.0 daqp typing_extensions mujoco==3.11.0                    # 호스트 테스트용
PYTHONPATH=$PWD:/DATA/ykkim/vendor_py/mink_host env_isaaclab/bin/python -m pytest -q igris/umi_walklow_replay

에피소드 7(각 1회, 렌더 포함): 두 IK 모두 3단으로 쌓았고 세 번째 박스가 기록 위치에서 10 cm(numpy) / 15 cm(mink) 벗어나
"기록 위치"는 둘 다 2/3. mink 쪽은 팔 관절 한계 접촉 18%(numpy 30%), 구 겹침 0%(31%), 허리 숙임 19%(39%), 손 오차 p99 6 mm(17 mm).
영상: `/DATA/ykkim/outputs/umi_walklow_replay/umi_walklow_replay_20261123_201020_e7_mk`(mink),
`…_201018_e7_np`(numpy), 비교 이미지는 mink 폴더의 `mink_vs_numpy_front.jpg`.

- numpy IK에서는 오른 위팔이 몸통 충돌 모델과 최대 6~19 mm 겹친 채 움직였다(어깨 roll 안쪽 한계가 곧 접촉 위치다).
  mink는 그 전에 멈추므로 어깨 roll 한계 접촉이 0%가 되고, 허리 숙임과 골반 이동도 줄었다.
- LowCmd 99~100 Hz, QP 완화 0회. 횟수가 적어(3회씩) 성공률 차이는 아직 말할 수 없다.
- 팔꿈치가 어깨선 안쪽인 시간(64%)과 관절 속도(p99 약 2.2 rad/s)는 그대로다. 속도·가속도 제한은 아직 넣지 않았다.
- 주의: mink 패키지 폴더를 느린 디스크에서 처음 읽는 동안 같은 디스크에 기록하는 시뮬이 멈출 수 있다
  (동시에 12개를 돌린 첫 시도에서 6건이 `stale native physics clock`으로 실패, 이후 재현되지 않음).

남은 것: 보행 모드로 서 있는 동안 발이 벌어지고 로봇 위치가 움직여서, 대부분의 실행에서 발이 케이스나 롤테이너
바닥판에 닿는다(55~190 N). 받침을 3~4 cm 더 떼어도(박스가 받침 밖으로 걸침) 달라지지 않아 되돌렸다.

벌어짐은 박스를 든 구간이 아니라 빈손 구간에서 생겼다(왼팔 스위블 중앙값: 든 구간 8°, 빈손 구간 58°).
빈손일 때 사람 손의 방향까지 그대로 따르느라 손목 yaw가 한계에 붙고 팔꿈치가 밀려 나간다. 그래서

- 손 방향은 박스에 접근하기 1초 전부터 놓은 뒤 1초까지만 온전히 따르고, 그 밖의 빈손 구간에서는 약하게만 따른다
  (`retarget.orientation_weight`, 목표 파일의 `orientation`). 손 위치는 항상 따른다.
- 팔 자세 기준은 고정값 대신 텔레옵 기록에서 찾는다: 지금 명령하는 손 포즈와 가장 비슷한 손 포즈 24개의 팔 관절을
  평균한다(몸통 좌표계, 오른팔은 왼팔로 뒤집어 한 표를 쓴다). 표는 `teleop_posture.npz`(place 과제 220개 에피소드,

## 기록 손 프레임 보정 (`hand_calibration.py`, 기본 켬, 2026-11-23 밤)

증상(사용자 지적): 박스를 잡기 직전에 왼손만 아래로 방향을 틀었다가 오른손과 평행해지며 잡으러 간다.

**원인은 IK가 아니라 기록(트래킹)이다.** 두 손 장치의 프레임이 일정하게 어긋나 있다. 34개 에피소드에서 박스를 든
22,415 프레임을 보면:

| 왼손이 오른손과 다른 점 | 값 | 흩어짐 |
|---|---|---|
| 손바닥 축 둘레 회전 | 28.2° | 프레임 간 2.8°, 에피소드 평균 간 1.6° |
| 수평으로 놓인 박스를 잡은 순간의 원점 높이 | 4.9 cm 낮음 | 0.9 cm |

사람이 그렇게 잡았다면 이렇게 일정할 수 없다(빈손 구간에서도 같은 회전이 나온다). 재생하면 왼손이 오른손보다 손끝을
약 29° 더 내리고 8.7 cm 더 낮게 내려왔다가, 잡는 순간 양손을 수평·대칭으로 맞추는 재타깃 때문에 마지막 0.6초에
혼자 크게 돌아 올라왔다. IK는 목표를 1~3° 이내로 따라갔다.

보정(상수, 프레임마다 다르지 않다): 든 박스가 주는 조건만 쓴다.

1. 박스가 수평으로 놓여 있을 때 손바닥 법선은 수평이다 → 각 손 프레임에서 손바닥 축 방향을 구한다.
   (예전의 "양 손바닥을 잇는 방향 = 법선" 보정은 원점 어긋남이 섞여 법선이 수평에서 10~14° 기울어 있었다.)
2. 두 손은 같은 강체 박스를 잡는다 → 손바닥 축 둘레 회전이 같아야 한다. 어느 손이 맞는지는 알 수 없어서
   접근이 자연스러운 오른손을 기준으로 왼손을 −28.16° 돌린다.
3. 두 손바닥 중심을 잇는 선은 박스 축이다 → 그 선에 수직인 원점 오차(6.2 cm)를 양손이 절반씩 나눠 갖는다
   (양손 중점은 기록 그대로).

상수는 `hand_calibration.CALIBRATION`, 다시 재려면
`python -m igris.umi_walklow_replay.hand_calibration --dataset <데이터셋>`.

함께 바꾼 것: 양손의 자세는 위치보다 먼저(1.5초 전부터) 잡는 자세로 맞춰 간다(`grasp_turn_in_s`). 내려오면서 같이
돌기 때문에 마지막 0.6초에 몰리던 회전이 없어진다.

| 잡기 직전(12개 에피소드, 36회) | 보정 전 | 보정 후 |
|---|---|---|
| 마지막 0.6초의 손 회전, 왼손 / 오른손 | 43° / 26° | 8° / 7° |
| 0.6초 전 손끝 기울기 차(왼 − 오) | −29° ± 3° | 0° ± 1° |
| 0.6초 전 높이 차(왼 − 오) | −8.7 ± 1.0 cm | +1.0 ± 0.8 cm |
| 왼손이 다시 올라오는 높이 | 5.2 cm | 0.5 cm |

오프라인 12개 에피소드(속도 제한 켬, 케이스 0.77 m 포함)에서 재생 길이 ×1.15 → ×1.03, 손 오차 p99 1.7 → 1.2 mm,
팔 관절 한계 접촉 5% → 1.7%, 허리 숙임 구간 7% → 4%. 왼손의 급한 회전이 속도 제한에 걸리던 것이 없어졌다.

## 장면 치수 확인과 재시험 (2026-11-23 밤, 사용자 실측값 반영)

사용자 실측: 롤테이너 폭 92 cm, 쌓여 있는 박스는 지면에서 80 cm.

| 항목 | 장면에 있던 값 | 판정 |

## 관절 속도·가속도 제한 (`governor.py`, 기본 켬, 2026-11-23 밤)

기록된 손은 사람 속도로 움직인다. 시계대로 재생하면 팔 관절이 IK의 속도 한계(2 rad/s)에 붙어 다닌다.
텔레옵 관절 기록의 명령 속도는 p99 0.69 rad/s, 가속도는 p99 4.0 rad/s²다.

방식: 손이 지나는 경로는 그대로 두고 **재생 진행만 늦춘다**(진행 조절기). 매 주기 IK는 기록 경로에서 한 주기 앞의
목표로 관절 변화를 풀고, 그 변화가 한계를 넘으면 넘는 비율만큼 관절 변화와 기록 시간의 진행을 함께 줄인다.
손은 기록된 경로 위에 남고, 늦어진 만큼 재생 시간이 길어진다. 관절을 따로따로 자르지 않으므로 손이 경로를 벗어나지 않는다.

| 항목 | 기본 | 옵션 |
|---|---|---|
| 관절 속도 한계 | 1.0 rad/s | `--joint-speed` (0이면 시계대로 재생) |
| 빨라질 때의 가속도 한계 | 6 rad/s² | `--joint-acceleration` |

로그의 `path`가 기록 시간(초)이다. 분석은 든 구간을 이 값으로 찾는다. 관절 재생(`teleop.py`)에는 쓰지 않는다.

|---|---|---|---|---|---|---|---|
| 0.80 m (현재) | 시계대로 | 80.3 s | 2.0 / 2.0 rad/s | 33 / 227 rad/s² | 3.4 mm | 3% | 8% |

## 숙임 → 골반 후퇴 되먹임 차단 (`anchoring.py`, 기본 켬, 2026-11-24, 시뮬레이션)

**무엇이 일어났나.** 2026-11-23의 실패 2회(6회 중)는 모두 세 번째 박스를 집는 순간이다.

손·케이스 접촉력은 13 N 이하였다. 밀린 것이 아니라 보행 제어기가 물러선 것이고, 방 고정 보정이 그만큼 손 목표를

**고친 것.**
1. **상체가 포화된 동안의 후퇴는 따라가지 않는다**(`anchoring.ReachHold`, `--anchor pelvis`에서 기본).

   손은 그만큼 방 기준 목표에 못 미친다(`shortfall`, 로그에 기록). 골반이 돌아오면 먼저 그 몫을 줄이고,

## 1층 박스에서 손이 케이스에 닿는 문제: 관절 유격 보정과 받침면 여유 (2026-11-24, 시뮬레이션)

사용자 지적: "1층 박스를 파지할 때 로봇 손이 닿는다. IK에서 충돌을 고려해야 하는지, 트래킹이 그런 것인지."
에피소드 7의 같은 설정 6회(`rw_a`~`rw_f`)에서 확인한 현상은 이렇다. 케이스 위에 직접 놓인 맨 아래 박스를 잡을 때
오른손 접촉 평판이 케이스 윗면에 0.8~1.5초 얹혀 있었고(6~8 N, 6회 모두), 손은 박스 중간 높이보다 1~2 cm 낮게 잡았다.
위층 박스에서는 손 아래에 아무것도 없어서 드러나지 않았다.

원인은 둘이고, 크기가 다르다.

| 원인 | 크기 | 근거 |
|---|---|---|
| **실행 쪽(주원인): 제조사 시뮬 모델의 관절 유격.** 링크 각 = 모터 각 + 유격 관절 각인데 IK는 모터 각으로 푼다. 유격 관절의 한계가 무르기 때문에 팔 무게로 어깨·팔꿈치 pitch 유격이 항상 약 1.2° 눌려 있다(범위는 ±0.29°) | 손이 목표보다 중앙값 24 mm 낮고(16~35 mm) 옆으로 16~19 mm | 기록된 모터 각에 유격 각을 더해 기구학을 풀면 물리의 손 위치와의 차이가 (10, 5, −24) mm → (1, 0, −5) mm |
| **기록 쪽: 사람 손바닥 경로가 케이스에 가깝다.** 로봇 손은 손바닥 점에서 10 cm 더 뻗은 강체라, 기록대로 가면 잡기 0.8초 전 오른손 평판과 케이스 사이가 4 mm다(왼손 37 mm) | 4 mm | 목표를 명목 장면에 놓고 손 형상의 최저점을 계산 |

IK 자체의 오차는 원인이 아니다(손 위치 오차 p95 0.8 mm). 목표는 잡기 전에 박스를 침범하지 않는다.

수정(둘 다 기본 켬):

- **관절 유격 보정**(`slack.py`): 모터 목표 = IK가 원하는 링크 각 − 측정한 유격 각. 유격 각은 관측기가 쓰는
  `run/joint_offsets.bin`(약 30 Hz, 시뮬 실측)에서 읽고 0.15초 저역통과한다. 준비 자세 뒤 2초에 걸쳐 들어온다.
  끄려면 `--no-slack-compensation`. 관절 재생(`teleop.py`의 `--joints`)에는 쓰지 않는다.
- **받침면 여유**(`clearance.py`): 손 접촉 평판이 케이스 윗면·롤테이너 적재면에 2 cm보다 가까워지는 구간에서 목표
  높이만 모자란 만큼 올린다(오르내림 5 cm/s 이하). 에피소드 7에서는 맨 아래 박스를 잡기 직전 0.96초 동안 오른손을
  최대 20 mm, 첫 박스를 놓고 빼는 0.6초 동안 14 mm 올린다. 값은 `--support-clearance M`(0이면 끔), 올린 양은

## 보행 모듈의 heading 모드 (`--heading-hold`, 선택 기능, 2026-11-24, 시뮬레이션)

사용자 지적: "왼발이 계속 밀린다. 보행 정책에 heading 옵션이 있고 하체가 뒤틀리는 것을 막아준다는데 적용해 보라."

**있는 기능이고, 켤 수 있다.** 제조사 제어기(`igris_c_controller/sim`, `real` 둘 다)의 `WalkModuleV3`·`WalkModuleV5`에
`setHeadingMode(bool, double)`이 있다. 켜면 보행 정책의 회전 속도 명령이 `2 × (목표 heading − IMU heading)`이 되고
±1 rad/s로 제한된다. 다른 회전 명령과 같이 0.2 rad/s 미만은 버려지므로 heading 오차 0.1 rad(5.7°) 안에서는 명령이 없다.
이 빌드에는 켜는 경로가 없다(설정 키·SDK 메시지·조이스틱 없음, 바이너리 안에 호출하는 곳도 없음). MuJoCo 프로세스가
아니라 제어기 프로세스에 있다. `native/heading.cpp`가 제어기 프로세스에 preload되어 내보내진 vtable 심볼로 모듈 객체를
찾고 제조사 setter를 직접 부른다(제조사 파일은 바꾸지 않는다, 네트워크 없는 시뮬 컨테이너에서만).

**IMU는 몸통에 있다.** 허리 3축 위라서 이 모드는 골반이 아니라 몸통 방향을 지킨다. 목표를 고정하면 재생이 허리를
60° 돌릴 때 다리가 그만큼 반대로 돈다(첫 시험: 골반이 +48°와 −100° 사이를 오감). 그래서 워커는 매 틱
"골반이 배치 때 방향을 향할 때의 몸통 heading"을 목표로 보낸다(`heading.py`, 측정한 허리 각으로 계산).

**보정은 발을 디뎌서 한다.** 오차가 5.7°를 넘으면 정책이 제자리에서 발을 디디며 돈다. 박스를 든 채 디딘 실행에서는
골반이 17~22 cm 움직여 박스 3개 중 2개를 놓쳤다(3회 중 1회, 발 디딤 14회). 그래서 손이 비어 있는 구간(놓은 뒤부터
다음 접근 전까지, 재생의 36~38%)에서만 보정하고, 그 밖에서는 "지금 골반 방향"을 목표로 보내 명령이 나오지 않게 한다.

## 텔레옵으로 다시 학습한 FiSTA 팔꿈치 prior (`--elbow-prior teleop`, 선택 기능, 2026-11-24)

사용자 요청: "FiSTA를 텔레옵 관절 기록으로 이 task에 맞게 재학습해서 mink QP에 넣어라." 팔 자세 기준을 조회 표 대신
학습된 망이 내게 하는 것이다. **기본은 여전히 조회 방식이다**(아래 시뮬 결과 때문).

**학습.** 데이터는 텔레옵 `Igris_Teleop_Box_Palletizing`(full-signals-15hz) 834개 에피소드의 관절 명령이다. 15 Hz를
30 Hz로 올리고(Catmull-Rom 중간점) 망이 실행 때 받는 것과 같은 형식(팔마다 손·팔꿈치 포즈, 몸통 축, 어깨 기준)으로
묶는다(`elbow_data.py`). 녹화 세션 51개를 통째로 나눠 학습 72만 / 검증 9.9만 / 시험 10.7만 창. 망·손실·최적화는
`igris/hl_ik`의 FiSTA 그대로다(`elbow_train.py`). A100 서버 GPU 5번 한 장, 컨테이너 안에서만 학습했다(시드 4개 병렬 12분;
`/DATA/ykkim/outputs/hl_ik_teleop_20261124/a100_ops/README.txt`에 컨테이너 명령).

**그대로 재학습하면 연속 실행에서 못 쓴다.** FiSTA는 과거 5스텝의 손 *과 팔꿈치*로 다음 팔꿈치를 낸다. 30 Hz에서
팔꿈치는 한 스텝에 0.4 mm밖에 안 움직여서, 망은 "팔꿈치는 직전 자리 근처"를 배우고 한 스텝 예측은 0.6 mm로 맞춘다.
그런데 실행 때 과거 팔꿈치는 자기 출력이다. 어긋나도 되돌리는 힘이 없어, 시험 세션에서 IK와 함께 굴리면 prior가
없을 때보다도 나쁘다. 그래서 두 가지를 더 학습했다.

- 스위블 보강: 학습 창의 과거 팔꿈치를 어깨–손 축 둘레로 무작위 회전(5~40°). 나아지지만 조회에 못 미친다.
- **손만 보기(채택)**: 과거 팔꿈치 입력을 가린다(학습 평균으로 대체, 실행 때도 같음). 예측이 손 이력과 다음 손 목표만의
  함수가 되어 어긋남이 쌓일 통로가 없다. 한 스텝 오차는 8.7 mm로 가장 크지만 연속 실행에서 가장 좋다.

시험 세션의 텔레옵 에피소드 16개, 기록된 손 포즈를 IK(mink)에 넣었을 때 팔꿈치가 작업자 명령과 떨어진 거리:

| 팔 자세를 정하는 것 | 팔꿈치 거리 평균 (왼/오) | p95 | 스위블 차이 | 한 스텝 예측 오차 |
|---|---|---|---|---|
| 없음(고정 자세) | 3.8 / 2.7 cm | 6.3 / 6.0 | 13° / 8° | |
| 조회 표(학습 세션만으로 만든 것) | 2.0 / 1.5 cm | 5.0 / 3.8 | 6.1° / 4.3° | |
| FiSTA, 사람 동작으로 학습(기존) | 4.0 / 4.7 cm | 7.7 / 12.0 | 13° / 15° | 2.9 mm |
| FiSTA, 텔레옵으로 그대로 재학습 | 3.8 / 3.2 cm | 7.5 / 7.4 | 14° / 9° | 0.6 mm |
| + 스위블 보강 20° | 2.6 / 2.6 cm | 5.4 / 5.5 | 9° / 8° | 0.9 mm |
| **손만 보기 (시드 42)** | **1.6 / 1.7 cm** | 3.5 / 3.6 | 4.1° / 4.0° | 8.7 mm |

손만 보기의 다른 세 시드는 1.55~1.67 / 1.70~1.80 cm. 조회와 같은 수준이다(왼팔은 조금 낫고 오른팔은 조금 못함).

**mink QP에 넣는 방식.** 예측 팔꿈치 위치를 각 팔의 영공간(손을 고정한 채 가능한 스위블) 관절 스텝으로 바꾸고, 그
스텝을 QP의 팔 자세 항이 요구한다(`mink_ik._swivel_step`). 조회 방식이 들어오는 것과 같은 통로다.
팔꿈치를 위치 과제로 넣는 방법은 세 가지를 해 봤고 모두 버렸다: QP가 허리를 돌려서 팔꿈치를 맞추려 한다(닿지 않는 목표에서
허리 yaw 7~20°). 스위블은 초당 오차의 4배율(조회와 같은 속도), 관절당 속도 한계의 1/4까지만 쓴다.

**예측을 믿을 수 없을 때는 조회 자세로.** 예측이 팔이 갈 수 있는 곳에서 멀면(스위블 방향에서 2~6 cm 벗어나거나 전체
4~12 cm 떨어짐) 그만큼 스위블을 줄이고, 줄인 몫은 조회 자세가 채운다. 시뮬에서 세 번째 박스를 높이 옮길 때 예측이
6~18 cm 벗어났고, 그것을 따라가면 오른팔 스위블이 114°까지 돌아 관절 한계에 붙었다.

### 스위블 각을 내는 변형 (`--elbow-prior swivel`, 2026-11-24 밤)

사용자 질문("예측 팔꿈치를 해결할 방법은 없나")에 따라, 망이 팔꿈치 *위치* 대신 팔마다 *스위블 각* 하나를 내도록 바꿔
다시 학습했다(`elbow_train.py --output swivel`, 손만 보기, 마지막 층만 1차원, 라벨은 기록된 팔의 `posture.swivel_deg`).
손이 고정되면 팔꿈치의 자유도는 어깨–손 축 둘레의 회전 하나뿐이므로, 어떤 각이 나와도 팔이 취할 수 있는 자세다.
실행 때는 예측 각을 학습 라벨의 1~99% 범위(왼 4.2~50.0°, 오 3.5~37.4°)로 자르고, 지금 팔꿈치를 그 각 쪽으로 한 번에
15°까지만 돌린 자리를 QP의 스위블 스텝 목표로 준다(`elbow_prior.swivel_elbows`). 그 뒤 경로는 위와 같다.
학습은 A100 GPU 5번 컨테이너에서 시드 4개, 각 2.5~3.5분(검증 오차가 1~8에폭에서 최저라 일찍 멈춤).

| | 조회 | 손만 보기, 팔꿈치 위치 | **손만 보기, 스위블 각** |
|---|---|---|---|
| 시험 세션 한 스텝 스위블 오차 | | 3.2~3.4° | 3.1~3.4° |

| 〃 스위블 차이 | 6.1° / 4.3° | 4.1° / 4.0° | 3.6° / 4.1° |
| 〃 예측 목표와 팔꿈치의 차이 | | 0.46 cm | 0.16 cm |
| UMI 12개: 예측 목표와 팔꿈치의 차이 | | 1.2 cm | 0.5 cm |

| 시뮬: 예측이 온전히 쓰인 시간 | | 61% | 74~100% |

스위블 각 변형의 다른 세 시드는 연속 실행 팔꿈치 거리 1.58~1.65 / 1.66~1.81 cm.

- **팔이 갈 수 없는 예측은 없어졌다.** 시뮬에서 예측 목표와 팔꿈치의 차이는 중앙값 0.2~0.9 cm(위치 출력일 때 세 번째 박스
  구간에서 6~18 cm), 스위블이 114°까지 가는 일도 없다. 조회 자세로 대체되는 일이 거의 없다.
- **적재 성공률은 조회와 구별되지 않는다.** 조회 8/9(앞선 6/6 + 같은 묶음에 섞어 돌린 3회 중 2회), 스위블 각 7/9(4/6 + 3/3).
  양쪽 실패 3회 모두 보행 중 발이 27~60° 돌아간 실행이고, 그때 손 오차와 스위블은 평소 수준이었다(팔 자세가 아니라
  아래 "알아둘 한계"의 골반 회전 문제).
- 분포 안 정확도는 위치 출력과 같다(한 스텝 스위블 오차 3.1~3.4°): 손 이력만으로 스위블을 맞히는 한계가 그 정도다.
- 기본은 여전히 조회 방식이다. 학습 prior가 조회보다 나은 점이 수치로 확인되지 않았다.

사용: `run.py all … --elbow-prior teleop` 또는 `--elbow-prior swivel`(이름 없이 `--elbow-prior`만 주면 기존의 사람 데이터 체크포인트). 체크포인트는
`/DATA/ykkim/outputs/hl_ik_teleop_20261124/training/teleop_hands/seed_42/best.pt`(teleop)와
`…/training/teleop_swivel/seed_42/best.pt`(swivel), 다른 파일은 `--checkpoint`.
학습 데이터 묶기는 `python -m igris.umi_walklow_replay.elbow_data --dataset … --out …`, 평가 도구와 결과는
`/DATA/ykkim/outputs/hl_ik_teleop_20261124/eval/`(`prior_eval.py`, `teleop_test_final.json`, `umi_final.json`, `sim_runs.txt`).

## 포즈만 받는 실시간 실행: 전처리 라벨과 포즈 스트림 (`labels.py`, `stream.py`, `--stream`, 2026-11-24 밤)

사용자 질문: "UMI 데이터를 pose만으로 학습했을 때 추론 과정에서 문제없이 joint 명령을 전달할 수 있는가, VR 텔레옵도
마찬가지" → "목표 다듬기·속도 제한을 전부 전처리해서 다시 학습하고, 정말 pose 값만 들어오는 실시간 조건을 확인".
지금까지의 재생은 그 조건이 아니었다. 에피소드 전체를 알고 있다는 점을 아래처럼 썼다.

| 재생이 하던 일 | 실시간에서 못 하는 이유 | 옮긴 곳 |
|---|---|---|
| 든 구간 기준의 목표 다듬기(양손 쌍, 집을 때·놓을 때 수평, 파지 높이, 잡기 0.6초 전부터 맞춤, 빈손 3 cm 벌림, 받침면 여유) | 든 구간은 에피소드 전체에서 찾고, "0.6초 뒤에 잡는다"는 미래다 | 라벨 |
| tracking 결함 보정 | 앞뒤 프레임이 필요하다 | 라벨 |
| 관절 속도 제한: 재생을 늦춤 | 들어오는 포즈의 시계는 늦출 수 없다 | 라벨의 시계 + 실행기 QP의 속도 경계 |
| 빈손 구간에서 손 방향을 4%만 따름 | 지금이 빈손 구간인지 모른다 | 라벨의 손 방향 자체 |
| 팔꿈치 prior에 33 ms 앞 손 목표를 줌 | 앞을 볼 수 없다 | 스트림의 최신 샘플 |
| 골반 위치로 목표를 방에 고정 (시뮬 실측) | 실기에 그 측정이 없다 | 실행기 밖: 포즈를 보내는 쪽의 눈을 대신하는 것으로 남김(`--anchor none`으로 끔) |
| 관절 유격 각 (시뮬 실측) | 〃 | 교정 상수(`--slack calibrated`) |

### 전처리 라벨 (`labels.py`)

다듬은 목표(`prepare.shape`)를 재생과 똑같은 설정(mink QP, 속도 1 rad/s·가속도 6 rad/s² 제한에 따른 감속, 빈손 방향 완화,
텔레옵 조회 자세, 관절·결합 한계, 자기충돌)으로 오프라인에서 풀고, **그때 로봇 모델이 갖는 손 포즈를 라벨로 삼는다.**
그래서 라벨은 구성상 "모든 한계 안의 관절 경로 하나가, 라벨의 시계대로, 실제로 내는 포즈"다. 손 방향은 박스 근처에서는
다듬은 목표 그대로이고 빈손 구간에서는 팔이 편한 방향이다. 감속 때문에 라벨 시계는 기록보다 군데군데 느리다:
각 라벨 샘플이 기록의 어느 시각을 보여 주는지(`source_t`)를 함께 저장하므로 **카메라 프레임은 그 시각으로 다시 뽑아야 한다.**

```bash
env_isaaclab/bin/python -m igris.umi_walklow_replay.labels \
  --dataset /DATA/ykkim/datasets/Box_palletizing_UMI_macos_intern_merged --out <새 폴더> --jobs 34
```

34개 에피소드 전부 만들어졌다(실패 0, 88코어에서 약 3분): `/DATA/ykkim/outputs/umi_pose_labels_20261124/labels/`.

| | 34개 에피소드 (최소 / 중앙 / 최대) |
|---|---|
| 길이: 기록 대비 라벨 | ×1.02 / ×1.03 / ×1.09 (합계 2,885 s → 2,982 s) |
| 라벨 뒤 관절 경로의 최고 속도 | 전부 1.00 rad/s |
| 박스 근처에서 다듬은 목표와의 차이 p99 | 0.7 / 1.4 / 8.4 mm (최대 9.2 mm, 에피소드 22) |
| 팔 관절이 한계에 닿은 시간 | 0 / 2.5 / 14.2 % |

`episode_XXX.npz`의 내용: `state`(N×15, 데이터셋 `observation.state`와 같은 배열 — 왼손 xyz + xyzw, 오른손 xyz + xyzw,
마지막 칸은 head.yaw 자리에 풀이의 몸통 방향; 데이터셋과 같은 15 Hz), `state_source_t`, `state_q`(같은 시각의 31축 관절),
100 Hz 라벨(`t`, `source_t`, `left`, `right`, `head_yaw`, `q`), 비교용 `raw_state`(상수만 적용한 원본)와 `shaped_*`(다듬은 목표).
손 프레임은 사람 손바닥이 아니라 로봇 EE 프레임이고, 높이는 기록 기준이다(WALK_LOW로 선 로봇의 골반 기준으로는 z에
`base_offset_z` 0.0315 m를 더한다; 시뮬 워커는 실행마다 잰 골반 높이를 쓴다).

### 실행기 (`stream.py`, 워커 `--stream-hz`)

`PoseStream`은 샘플을 도착하는 대로 받고 "지금의 목표"만 내준다. 샘플 사이에서는 목표가 지금 있는 곳에서 최신 샘플까지
한 주기에 걸쳐 직선으로 간다. 그래서 목표는 소스보다 한 주기(15 Hz에서 67 ms) 늦고, 도착하지 않은 샘플보다 앞설 수 없다
(테스트: 스트림을 중간에서 잘라도 그 전까지의 명령이 비트 단위로 같다). 워커의 스트림 모드에서 달라지는 것:

- 재생을 늦추지 않는다. 관절 속도 제한(`--joint-speed`, 1 rad/s)은 **QP의 속도 경계**가 된다: 포즈가 더 빠른 움직임을
  요구하면 손이 잠깐 뒤처진다. 처음에는 경계를 풀이기의 2 rad/s로 두었는데, 골반이 움직여 방 고정 목표가 달아날 때 팔이
  2 rad/s로 쫓아갔고 3회 중 1회 박스를 떨어뜨렸다(아래 표).
- 손 방향은 항상 온전히 따른다. 든 구간 정보도 앞 보기도 없다. 팔꿈치 prior를 쓰면 그 목표는 스트림의 최신 샘플이다.
- 스트림을 물릴 때 1초 동안 첫 포즈로 1 rad/s 이하로 다가간다(방 고정이 골반 기울기도 되돌려 첫 목표가 준비 자세에서
  3~4 cm 떨어져 있다).
- 조회 자세·자기충돌·관절 한계·결합 한계는 그대로다(모두 현재 값만 쓴다).
- `--slack calibrated`: 유격을 시뮬 실측 대신 상수로(어깨 pitch 1.08°/1.10°, 팔꿈치 pitch 1.17°/1.14°; 재생 5회의 평균.
  무게를 받는 이 네 관절만 늘 한쪽에 눌려 있고(실행 안 표준편차 0.25°), 나머지 유격은 0 주위로 흔들려 상수가 없다).

```bash
# 준비한 출력의 목표를 라벨·스트림으로 바꾸고(`labels`), 그 스트림을 한 샘플씩 받는 조건으로 재생
env_isaaclab/bin/python -m igris.umi_walklow_replay.run all --out $OUT --dataset … --episode 7 --stream
# 다른 스트림 파일(예: 정책 출력), 0.2초 늦게 도착, 시뮬 실측 없이
env_isaaclab/bin/python -m igris.umi_walklow_replay.run replay --out $OUT --stream <stream.npz> --stream-latency 0.2 \
  --slack calibrated --anchor none
```

### 대역 행동모델 (`pose_policy.py`)

VLA는 여기서 학습하지 않았다(영상 파이프라인과 프레임 재추출이 필요하고, 시뮬에 로봇 카메라 영상이 없다). 대신 전처리
라벨로 **영상 없는 포즈 전용 모델**을 학습해 "모델이 낸 포즈"를 만들었다: 최근 8개 포즈(0.53 s) → 다음 16개 포즈(1.07 s)의
변화량을 내는 MLP(512×3). 30개 에피소드로 학습, 4개(7, 13, 21, 29)는 보류, CPU 약 2분(검증 손실은 19에폭에서 최저).
실행은 정책을 로봇에 올릴 때처럼 한다: 4샘플(0.27 s)마다 새 묶음, 묶음은 관측에서 2샘플(0.13 s) 뒤에 도착. 관측으로는
보류 에피소드의 라벨 이력을 넣는다(학습한 정책을 기록 관측으로 오픈루프 검증하는 방식). 따라서 이 모델은 "라벨로 학습한
망의 출력이 갖는 오차·묶음 경계·지연"을 실행기에 주는 용도이고, 박스를 보고 찾아가는 능력은 없다.

| 보류 에피소드 4개, 모델 스트림 대 라벨 | 묶음을 그대로 이음 | 겹치는 구간을 섞어 이음(`--blend`) |
|---|---|---|
| 손 위치 차이 중앙 / p99 / 최대 | 0.6~0.7 / 2.1~2.9 / 3.4~6.1 cm | 0.7~0.9 / 2.3~3.5 / 3.4~6.1 cm |
| 손 방향 차이 p99 | 4.4~5.7° | 5.3~5.9° |
| 한 샘플 사이 이동 최대 (라벨 1.8~1.9 cm) | 4.9~6.9 cm | 2.2~3.7 cm |

```bash
env_isaaclab/bin/python -m igris.umi_walklow_replay.pose_policy train --labels <라벨 폴더> --out <새 폴더>
env_isaaclab/bin/python -m igris.umi_walklow_replay.pose_policy run --labels <라벨 폴더> --checkpoint <폴더>/policy.pt --out <새 폴더> [--blend]
```

34개 에피소드, 값은 에피소드 중앙값(괄호는 가장 나쁜 에피소드). 손 오차는 실행기가 받은 목표(한 주기 전의 소스) 기준이다.

보류 에피소드 4개에서 모델 출력을 넣으면: 손 위치 오차 p99 1.2 (2.3) mm·최대 4.2 (6.6) mm, 속도 경계 4.3% 틱. 섞어 이으면
p99 0.9 (2.0) mm·최대 1.8 (4.0) mm, 2.0% 틱. 속도 경계를 2 rad/s로 두면 라벨은 관절 속도 p99 0.99 rad/s(구성대로),
모델 출력은 1.42 (1.95) rad/s까지 쓴다 — 망의 출력은 라벨이 지키는 속도를 지키지 않으므로 경계는 실행기에 있어야 한다.

읽는 법: **IK 수준에서는 어느 스트림이든 실시간으로 풀리고 모든 한계가 지켜진다.** 전처리가 주는 차이는 오차의 꼬리다
(최대 2.4 mm 대 16 mm·108 mm). 원본의 108 mm는 tracking 점프가 그대로 들어온 것이고, 원본에는 파지에 필요한 조임과 수평
맞춤이 없다 — 이쪽은 IK가 아니라 접촉에서 드러나는 문제라 시뮬로는 돌리지 않았다.

### 시뮬: 에피소드 7 (제조사 WALK_LOW, 3단 적재 = 박스 3개가 모두 쌓여 서 있음)

|---|---|---|---|---|---|---|
| 기존 재생: 에피소드 전체를 봄 (`ra`) | 6 / 6 | 18 / 18 | 78.7~83.4 s | 1.1~9.9 mm | 16~18 rad/s² | 1.0~1.3 % |

| **라벨 스트림 15 Hz, 경계 1 rad/s (`lb`)** | **9 / 9** | 27 / 27 | 75.4 s | 0.7~34 mm | 20~53 rad/s² | 1.3~2.8 % |
| 〃 0.2초 늦게 도착 (`lt`) | 4 / 6 | 16 / 18 | 75.6 s | 0.8~53 mm | 21~191 rad/s² | 1.6~14.3 % |

| 모델 출력 스트림 (`mo`) | 5 / 6 | 17 / 18 | 75.4 s | 1.3~45 mm | 54~126 rad/s² | 11~19 % |
| 모델 출력, 묶음을 섞어 이음 (`bl`) | 6 / 6 | 18 / 18 | 75.4 s | 1.0~32 mm | 31~102 rad/s² | 7.0~9.6 % |

스트림 조건은 모두 한 샘플씩 받고, 앞을 보지 않고, 시계를 늦추지 않고, 든 구간 정보 없이 돌았다. 명령 주기는 93.6~99.7 Hz
(6개 동시 실행). 표의 조건 이름 뒤 글자는 `sim/runs.txt`의 실행 꼬리표다.

- **포즈만 한 샘플씩 받아도 쌓인다.** 라벨 스트림 9/9, 걸린 시간은 라벨 길이 그대로다(기존 재생은 감속으로 78.7~83.4 s).
- **IK 손 오차 p99가 큰 실행(13~34 mm)은 골반이 물러나 방 고정 목표가 멀어진 몇 초다**(주로 세 번째 박스, 허리 숙임이 한계
  8.6°). 기존 재생은 그때 시계를 늦춰 기다리므로 오차 대신 시간이 늘고, 스트림은 기다릴 수 없어 손이 그만큼 못 미친다.
  한 실행의 중앙값은 0.06~0.14 mm로 재생(0.07~0.10 mm)과 같다.
- **조건 사이의 성공률 차이는 이 표본으로 구별되지 않는다.** 골반 보정을 쓴 스트림 33회 중 실패 4회(지연 2, 유격 상수 1,
  모델 1)는 모두 세 번째 박스에서, 골반이 22~37 cm 움직이고 20° 넘게 돈 실행이다 — 기존 재생에서도 나오는 보행 쪽
  실패다(오늘 기존 재생 15회 중 1회, "알아둘 한계"). 0.2초 지연은 스트림 전체가 그만큼 늦을 뿐 되먹임이 없어 결과를 바꿀
  이유가 없고, 유격 상수에서도 손이 케이스에 얹힌 실행은 없다(0/6; 유격 보정이 없던 때는 6/6).
- **골반 보정을 빼면 1/6이다.** 이때 IK 오차는 가장 작다(0.6~0.7 mm): 실행기는 받은 포즈를 정확히 낸다. 그런데 보행 중
  골반이 12~31 cm 움직이므로 손이 방에서 그만큼 어긋난다(놓는 자리 9~10 cm 어긋남, 세 번째 박스를 못 집음). "포즈만"으로
  과제가 되려면 포즈를 보내는 쪽(정책의 카메라, 조종자의 눈)이 로봇 기준 포즈를 그때그때 고쳐 줘야 한다. 이 시험의 골반
  보정은 그 역할을 오차 없는 시각으로 대신한 것이고, 실제 정책·조종자가 그만큼 고쳐 주는지는 시험되지 않았다.
- **모델 출력은 쌓이지만 명령이 거칠다.** 적재는 5/6, 섞어 이으면 6/6으로 라벨과 구별되지 않는다. 그러나 묶음 경계마다
  목표가 튀어 관절 가속도 p99가 54~126 rad/s², 속도의 5 Hz 위 성분이 11~19%다(라벨 1.3~2.8%). 섞어 이으면 7.0~9.6%로
  줄지만 라벨 수준은 아니다. 관절 추종 오차(rms 0.014~0.018 rad)와 토크 p99(28~35 Nm)는 라벨과 같은 수준이다.
- 속도 경계를 2 rad/s로 둔 첫 시도(2/3)에서는 골반이 움직일 때 팔이 2 rad/s로 목표를 쫓았다. 재생 늦춤을 뺀 자리에는 QP의
  1 rad/s 경계가 있어야 한다.

확인하지 않은 것: 영상을 보는 실제 VLA(박스를 잘못 찾는 오차 등), 에피소드 7 이외의 시뮬, 전처리 없는 원본 스트림의 시뮬,
실기. 렌더 영상은 만들지 않았다(이 기간 PRO6000 GPU가 내려가 있었다).

평가 도구와 결과: `/DATA/ykkim/outputs/umi_pose_labels_20261124/`(`labels/`, `policy/`, `eval/realtime_eval.py`와 결과,
`sim/trial.sh`·`batch.sh`·`summ.py`·`table.py`·`runs.txt`).

## 로봇 카메라 시뮬 데이터와 상대 EE ACT (`cameras.py`, `ee_features.py`, `ee_dataset.py`, `act_ee.py`, `policy_server.py`, 2026-11-25)

UMI 에피소드를 로봇의 관절과 링크를 거친 EE 데이터로 바꾸고, 로봇 자신의 카메라 영상과 함께 시뮬 학습 데이터로 만든 뒤,
그 데이터로 ACT를 학습해 **상대 EE 행동만으로 로봇이 과제를 하는지** 시뮬 폐루프로 확인했다. 데이터 생성·학습·평가는 모두
A100 서버의 컨테이너 안에서 했다(GPU 5번 한 장, `/data3/ykkim/umi_act`). 실기는 움직이지 않았다.

```text
UMI 에피소드 ─ labels.py ─→ 로봇이 따라갈 수 있는 포즈 라벨(15 Hz)
  ─ 시뮬 재생(--stream, 방 고정 보정 = 시연자의 눈) ─→ 관절 각·손 목표·골반·몸체 포즈 기록
  ─ ee_dataset.py ─→ 프레임(15 Hz): 관절 → 링크 → EE(FK), 로봇 카메라 3대, 그 프레임의 목표
  ─ act_ee.py ─→ 상대 EE 행동 묶음(32샘플 = 2.1초)으로 ACT 학습
  ─ 폐루프: policy_server.py(카메라 + 관절 상태 → 행동 묶음) ⇄ worker --policy(IK → LowCmd)
```

폐루프에서 정책 쪽이 시뮬에서 읽는 것은 로봇이 실제로도 가진 두 가지뿐이다: 관절 각과 카메라 영상. 골반 위치, 물체 위치,
관절 유격 실측은 쓰지 않는다(`--anchor none`, `--slack calibrated`가 강제된다).

### 카메라 (`cameras.py`)

| 이름 | 붙인 곳 | 투영 |
|---|---|---|
| `left_cam`, `right_cam` | URDF의 손목 카메라 링크 `l_wrist_cam`, `r_wrist_cam`(`igris_c_description/urdf/igris_c_rcv_hand_pelvis.urdf`; 시뮬 모델에 같은 이름의 몸체가 있다). 광축은 링크 +z, 렌즈는 하우징 앞면(z = 27 mm) | 핀홀, 수직 화각 75°(가로 91°), 640×480 |
| `head_cam` | 몸통(`torso` 링크) 앞면 가운데: 링크 기준 x 0.115 m, z 0.21 m(어깨 관절 높이 0.266 m 바로 아래), 25° 아래를 봄 | 등거리(equidistant) fisheye, 화각 190°, 180° 원의 지름이 영상 폭의 0.92, 640×480 |

이름과 구성은 UMI 데이터셋의 `observation.images.*`(머리 fisheye 1 + 손목 2)를 따랐다. 손목 카메라의 화각과 영상에서 위쪽이
어느 축인지는 URDF에 없어 정한 값이다(하우징 메시가 32×32 mm 정면에 깊이 33 mm인 것에서 광축만 읽었다).

- 물리는 그대로 제조사 MuJoCo가 계산하고, 그림은 관측기가 쓴 몸체 포즈(`poses.bin`, 실행 중에는 `latest.bin`)를 같은 장면
  파일에 넣어 MuJoCo로 그린다(EGL, GPU). Isaac 렌더를 쓰지 않은 이유는 속도다: 폐루프에서는 15 Hz 관측마다 세 시점을
  그려야 하는데 이 경로는 세 시점에 18 ms, Isaac 렌더는 시점당 0.3초였다. 학습 데이터와 추론이 같은 렌더러를 써야 한다.
- MuJoCo에는 fisheye 카메라가 없어 90° 시점 다섯 장(앞·좌·우·위·아래)을 그려 등거리 영상으로 다시 뽑는다(`FisheyeMap`).
- 박스에는 장면의 텍스처(`scene/textures`)를 면별로 입혔다. MuJoCo의 큐브 텍스처는 정육면체가 아닌 박스에서 면을 넘어
  번지므로 박스는 면마다 텍스처 좌표를 가진 메시로 그린다. 로봇은 단색이다.

### 허리와 양팔의 표현 (`ee_features.py`)

정책이 보는 로봇은 "EE 세 개"다: 가슴(허리 3축이 정하는 몸통)과 두 손. 전부 관절 각에서 링크를 따라 계산한다.

| | 값 | 내용 |
|---|---|---|
| 상태 (30) | 왼손·오른손 포즈(각 9) | **가슴 프레임** 기준 위치 3 + 회전 행렬의 앞 두 열 6 |
| | 양손 쌍(9) | 왼손 프레임에서 본 오른손 |
| | 허리(3) | 허리 관절 각 yaw·roll·pitch |
| 행동 (21 × 32샘플) | 왼손(9) | 목표 포즈를 **관측 순간의 왼손 프레임**으로 표현(상대 이동) |
| | 양손 쌍(9) | 오른손 목표를 **왼손 목표의 프레임**으로 표현 |
| | 허리(3) | 허리 관절 목표 − 관측 순간의 허리 각 |

이렇게 정한 이유와 근거(시뮬 시연 데이터에서 잰 값):

1. **손은 상대 이동으로.** 방에 고정된 좌표가 로봇에 없다. 골반은 한 에피소드 동안 중앙값 20 cm·19° 움직이고(시연 137회),
   1.1 Hz로 흔들린다. 손의 상대 이동은 어느 좌표계에서 재도 같은 숫자이고(두 포즈가 같은 좌표계이기만 하면), 손목 카메라가
   보는 움직임과 같은 것이다. 상태도 방을 가리키는 값이 없다(가슴 기준 손, 허리 각).
2. **라벨은 방 기준으로 만들고, 실행은 골반 기준으로 한다.** 라벨은 "관측 순간의 손(방 좌표)에서 목표(방 좌표)까지"로
   만든다(시뮬의 골반 실측을 라벨 제작에만 쓴다). 실행기는 그 행동을 골반 좌표의 손 포즈에 얹는다 — 로봇이 스스로 아는
   것은 그것뿐이다. 묶음을 실행하는 동안 골반이 움직인 만큼이 오차가 되고, 다음 관측이 그것을 본다. 라벨까지 골반 좌표로
   만들면(명령된 그대로) 골반 흔들림의 보정분이 라벨에 섞인다: 두 라벨의 차이가 실행 구간(묶음 2~6번째 샘플)에서 중앙값
   5~10 mm, 95% 16~30 mm였다. 관측 한 장으로는 예측할 수 없는 성분이라 방 기준 라벨을 택했다(`--frame pelvis`로 바꿔 학습할 수는 있다).
3. **두 손은 한 쌍으로.** 박스는 두 손바닥이 양쪽에서 눌러서 든다. 든 동안 명령된 손 간격은 286 mm로 일정하고 실제 간격은
   307~319 mm다: 조임은 27 mm(21~32 mm). 쌍으로 주면 든 동안의 정답이 상수이고, 왼손 행동의 오차는 두 손과 박스를 함께
   옮길 뿐이다. **다만 손마다 상대 행동을 따로 내는 것(`--independent-hands`)보다 낫다는 것은 확인하지 못했다.** 같은
   학습량(4,000스텝)에서 보류 에피소드의 든 구간 손 간격 오차는 쌍 4.2 mm(95% 6.1 mm), 독립 3.9 mm(95% 9.5 mm)로 평균이
   같고(두 손의 오차가 같이 움직인다), 폐루프도 제자리에 놓인 박스 22/36 대 19/33으로 구별되지 않았다. 쌍 표현은 30,000스텝에서
   간격 오차 1.1 mm(95% 1.2 mm)까지 내려간다(같은 망의 왼손 오차는 21 mm); 독립 표현을 그만큼 학습한 것과는 비교하지 않았다.
4. **허리는 관절 목표로, 변화량으로.** 허리는 세 관절의 직렬이고 한계가 관절에 있어 포즈로 줄 이유가 없다. 절대 각이 아닌
   변화량인 이유는 손과 같다: 골반이 발 위에서 돌기 때문에 "롤테이너가 앞에 올 때까지 돌린다"는 살아남고 "허리 −60°"는
   틀린다. 실행기가 이 허리 목표를 어떻게 쓰는지는 네 가지를 비교했다(아래 표, `--waist`).

실행기(`policy_link.py`, `worker.py --policy`): 정책 프로세스는 제어기 시계로 4샘플(0.27초)마다 관측하고, 답한 묶음은
관측 뒤 2샘플째부터 쓰며(빨리 와도 늦게 와도 같게), 앞 묶음과 겹치는 4샘플은 섞어 잇는다. 시뮬 컨테이너는 네트워크가
없으므로 두 프로세스는 실행 폴더의 파일 두 개(`policy/state.bin`, `policy/chunk.bin`)로만 주고받는다. 손 목표는 기존
포즈 스트림과 같은 경로(`PoseStream` → mink QP, 관절 속도 경계 1 rad/s, 자기충돌·관절 한계)로 관절 명령이 된다.
정책의 답은 관측 뒤 평균 1.0샘플(95% 1.4샘플)에 도착했다(렌더 33 ms + 망 65 ms, 정책 프로세스 4개와 학습이 GPU를 같이 쓸 때).

**목표 속도 제한(`PairLimiter`, 기본 켬).** 묶음은 자기 관측의 측정 손 포즈에 얹히므로 묶음이 바뀌는 자리에서 왼손 목표가
한 샘플에 몇 cm씩 튈 수 있다. 그러면 관절이 속도 경계에 걸린 채 따라가는데 두 팔이 걸리는 정도가 달라, 목표로는 완벽한
한 쌍인 두 손이 실제로는 벌어질 수 있다(7,000스텝 정책의 한 실행에서 박스를 들어 올리는 동안 왼손 목표가 1.4 m/s로 움직였다;
시연은 0.4 m/s). 그래서 왼손 목표가 한
샘플에 움직일 수 있는 양을 시연의 99.9번째 백분위(26 mm, 3.6°)로 묶고, 오른손 목표는 왼손 목표 기준 자리를 그대로 지키게
했다. 같은 체크포인트(7,000스텝)·같은 장면 12회씩 비교: 적재 수는 같고(제자리에 놓인 박스 20/36 대 21/36) 명령은 시연
수준으로 고와졌다(IK 오차 p99 56 → 14 mm, 관절 가속도 p99 103 → 45 rad/s², 5 Hz 위 성분 18 → 10%). `--policy-step-limit 0`으로 끈다.

읽는 법:

- **상대 EE 행동만으로 로봇이 과제를 한다.** 시뮬에서 읽은 것은 관절 각과 카메라뿐인데, 같은 포즈 라벨을 눈 없이 재생한
  것의 두 배 가까이 놓는다(보류 61% 대 36%, 학습 69% 대 31%). 박스를 든 비율은 97%(67/69)다. 시연(골반 실측으로 방에
  고정)에는 못 미친다(85~94%).
- **차이는 세 번째 박스에 몰려 있다**(보류: 정책 5/23, 시연 10/16). 원인은 표현이 아니라 이 시뮬의 접촉이다: 쥔 박스가
  손 안에서 초당 약 1 cm씩 미끄러진다(쥐는 힘은 50~80 N으로 충분한데도; 시연의 첫 박스도 6초에 22 mm). 가장 낮은 데서
  가장 높이 옮기는 세 번째 박스는 시연에서도 손 안에서 87 mm 미끄러진 채 놓이고(전체 시연에서 세 번째 박스 성공 82/137),
  정책은 1~2초만 더 들고 있어도 놓친다. 보류 23회의 세 번째 박스: 제자리 5, 들었다가 다른 데(케이스 위로 다시, 또는 적재
  위에 어긋나게) 내려놓음 11, 바닥에 떨어뜨림 5, 들지 못함 2; 실패한 실행에서 박스는 중앙값 36 cm까지 올라갔었다.
- **절대 EE와는 성공률로 구별되지 않는다**(24/36 대 42/69). 다른 것은 명령의 질이다: 절대 행동은 묶음마다 3~5 cm씩 다른
  목표를 내서 관절 가속도 p99가 4배, 5 Hz 위 성분이 4배, 관절이 한계나 속도 경계에 걸린 시간이 3배다. 시뮬의 서보는 그래도
  따라가지만 실기에서 그대로 보낼 명령은 아니다. 학습 스텝은 다르다(15,000 대 30,000); 상대 EE는 7,000스텝에서도 가속도 45, 5 Hz 위 10%였다.
- 학습을 길게 해도 보류 장면은 나아지지 않았다: 7,000스텝 20/36, 30,000스텝 42/69. 보류 에피소드의 한 스텝 오차도 3,000스텝
  이후 평탄하다(왼손 2.1 cm·2.9°, 양손 쌍 1.0 cm·1.4°, 허리 0.7°). 시연 81회·장면 27개가 한도로 보인다.
- 같은 조건의 표본이 12~23회라 10%p 안팎의 차이는 구별되지 않는다. 한 에피소드 안의 실행끼리, 한 실행 안의 박스끼리는 독립이 아니다.

허리 목표를 실행기가 어떻게 쓰는가(`--waist`, 같은 망, 속도 제한 켬):

| 방식 | 뜻 | 보류 장면 | 학습 장면 | 3개 모두 (보류) | 골반 회전 중앙값 (보류) |
|---|---|---|---|---|---|
| `pinned` (기본) | 허리는 정책이 준 각으로 보내고, 팔만 그 가슴 위에서 IK | 42/69 (61%) | 25/36 (69%) | 5/23 | 46° |
| `reference` | 허리 세 관절의 선호 자세로만 넣고 허리·팔을 함께 IK | 49/69 (71%) | 16/33 (48%) | 7/23 | 21° |
| `yaw` | yaw만 선호 자세로, 숙임은 IK가 정함 | 27/39 (69%) | — | 5/13 | 39° |
| `free` | 정책의 허리를 쓰지 않음(손 목표만) | 19/36 (53%) | — | 0/12 | 52° |

`pinned`과 `reference`는 보류 장면과 학습 장면에서 순위가 뒤집히고 합치면 67/105 대 65/102로 같다. `free`만 나쁘다: 두 번째
박스부터 무너진다(1·2·3번째 12/6/1). 즉 **허리는 정책이 명령해야 하고, 그 명령을 얼마나 엄격히 따르는지는 이 표본으로는
차이가 없다.** 기본은 정책의 명령을 그대로 내는 `pinned`으로 두었다.

양손 표현(같은 4,000스텝 학습, 보류 장면, 허리 고정 + 속도 제한): 왼손 + 쌍 22/36(3개 모두 2/12), 손마다 따로 19/33(3/11).
구별되지 않는다.

**확인하지 않은 것.** 실기. 실제 카메라 영상(시뮬 렌더로만 학습·평가했다). 시연 81회보다 많은 데이터에서의 성능. 절대 EE와
독립 손 표현을 같은 30,000스텝으로 학습한 비교. 묶음 길이·관측 주기·지연 보정 값의 다른 선택(32샘플·4샘플·2샘플만 썼다).
쥔 박스가 미끄러지는 접촉 모델을 고친 뒤의 세 번째 박스. 에피소드 8·12·30의 장면(시연이 한 번도 성공하지 못해 데이터에 없다).

영상(바깥 시점 + 로봇 카메라 3대, 보류 장면에서 3개 모두 쌓은 실행): `/DATA/ykkim/outputs/umi_act_20261125/videos/`.

### 시뮬 시연 데이터 (`container_run.py`, `ee_dataset.py`, `lerobot_export.py`)

- 시연은 전처리 라벨을 한 샘플씩 받는 포즈 스트림 재생이다(`--stream --slack calibrated`, 방 고정 보정 켬). 방 고정 보정이
  시연자의 눈 노릇을 한다: 시연에서만 쓰고 정책 실행에는 없다.
- 34개 에피소드를 4회씩 재생했고, 로봇이 서지 못한 15회는 다시 돌렸다(아래 "A100에서의 실행" 참고). 기록이 남은 137회 중
  **세 박스가 모두 쌓인 94회만 학습 데이터로 쓴다**(31개 에피소드; 8·12·30번은 한 번도 성공하지 못했다).
- 프레임은 스트림과 같은 15 Hz다. 프레임 `k`의 관측은 그 순간까지 알려진 것(가장 새 관절 상태, 가장 새 카메라 기록, 영상은
  최대 23 ms 전 것)이고, 행동은 그 순간 제어기에 넘겨진 스트림 샘플이다(한 주기 뒤 제어기가 도달해 있던 손 목표와 그때의 허리 명령).
- 손 포즈는 측정 관절 각 + 유격 교정 상수(`slack.calibrated`)로 FK를 풀어 얻는다. 시뮬의 손 실측 포즈는 쓰지 않는다.
- 실행별 결과는 `<출력>/dataset/`: `frames.npz`(관절 각, 손·가슴·골반 포즈, 목표), 카메라별 `*.mp4`(640×480)와 학습용
  작은 그림 묶음 `*.jpgs`(320×240 JPEG).
- LeRobot 형식(v3.0) 묶음은 `lerobot_export.py`가 만든다. 열: `observation.images.{head_cam,left_cam,right_cam}`,
  `observation.state`(30), `observation.ee_pelvis`·`observation.ee_room`(양손 포즈 18), `observation.joints`(31),
  `action`(골반 좌표의 손 목표 18 + 허리 관절 목표 3), `action.room`, `action.relative`(한 스텝 상대 행동 21), `action.joints`,
  `source.episode`. 상대 행동 **묶음**은 시작 프레임마다 달라 열로 둘 수 없다: `observation.ee_room`과 뒤 프레임들의
  `action.room`에서 `ee_features.relative_actions`로 만든다(`act_ee.py`가 그렇게 학습한다).

### 학습 (`act_ee.py`)

망은 LeRobot의 ACT 그대로다(ResNet18 × 카메라 3대, 묶음 32샘플, VAE 포함). LeRobot의 학습 스크립트를 쓰지 않은 이유는
행동 묶음이 관측 순간의 포즈에 상대적이라 프레임별 열로 저장할 수 없기 때문이다: 묶음 만들기와 정규화만 여기서 하고
체크포인트는 `ACTPolicy.save_pretrained` 형식(`config.json`, `model.safetensors`)에 정규화 통계 `stats.npz`를 더해 둔다.

- 입력 영상 320×240, 학습 때만 ±8픽셀 이동과 밝기·대비 변화, 상태에는 표준편차의 3% 잡음.
- 배치 64, AdamW 학습률 5e-5(워밍업 500스텝 뒤 코사인), 30,000스텝, 혼합 정밀도. A100 한 장에서 1시간 44분(평가와 내보내기가 GPU를 같이 쓰는 동안).
- 에피소드 7·13·21·29는 학습에서 통째로 뺐다(장면 4개, 시연 13회). 나머지 27개 에피소드의 시연 81회(105,495프레임)로 학습했다.

### A100에서의 실행

A100 호스트에서는 docker 명령과 rsync만 쓴다. 나머지는 전부 컨테이너 안에서 돈다.

| 컨테이너 | 이미지 | 하는 일 |
|---|---|---|
| 실행마다 하나, `--network none`, 코어 3개 고정 | `igris-sim:jazzy`(PRO6000에서 옮김) | `container_run.py`: 준비 → 라벨 → 제조사 시뮬 기동 → 재생 또는 정책 실행 → 판정. docker 호출 없이 컨테이너 안에서 전 과정을 돈다 |
| `ykkim_umi_act_gpu`, GPU 5번 | `ykkim/task_decomposition:20261117` | 카메라 렌더(EGL), 데이터셋 작성, ACT 학습, 폐루프의 정책 프로세스 |

- 호스트 쪽 스크립트는 PRO6000의 `/DATA/ykkim/outputs/umi_act_20261125/a100/`에 있다(`sync.sh` 코드 전송, `sim.sh` 시뮬 1회,
  `batch.sh`·`lane.sh` 여러 회 병렬과 재시도, `gpu.sh` GPU 컨테이너, `render.sh` 데이터셋 렌더). A100의 작업 폴더는
  `/data3/ykkim/umi_act`(`ws/` 코드, `DATA/` 데이터·출력; 컨테이너 안에서는 PRO6000과 같은 경로로 보인다).
- 이 서버의 CPU에서는 물리가 실시간의 0.65배로 돈다(제어 주기는 시뮬 시간 기준 약 91 Hz). 정책 응답 시간도 시뮬 시계로 잰다.
- GPU 컨테이너는 작업이 끝나 지웠다(`gpu.sh up`으로 다시 띄운다). 데이터와 출력은 A100의 `/data3/ykkim/umi_act/DATA`에 남아 있다(42 GB).

```bash
cd /DATA/ykkim/outputs/umi_act_20261125/a100
./sync.sh && ./gpu.sh up                                   # 코드 전송, GPU 컨테이너 기동
./batch.sh gen 8 - jobs/gen.txt                            # 시연 생성: 줄마다 "<이름> --episode N --stream --slack calibrated"
./render.sh gen                                            # 실행별 dataset/ (프레임 + 카메라 3대)
./gpu.sh run "python -m igris.umi_walklow_replay.act_ee train --runs /DATA/ykkim/outputs/umi_act/gen --out /DATA/ykkim/outputs/umi_act/train/main"
./batch.sh eval 8 /DATA/ykkim/outputs/umi_act/train/main/last jobs/held.txt     # 폐루프: 줄마다 "<이름> --episode N --policy --waist pinned --policy-seconds S"
./gpu.sh run "python /DATA/ykkim/scripts/summarize.py /DATA/ykkim/outputs/umi_act/eval"     # 실행별 판정과 명령 품질
```
- **7회에 1회꼴로 로봇이 서지 못한다**(이번 작업의 399회 중 54회). 그때는 물리 한 스텝이 0.7 ms가 아니라 12 ms 걸리고(물리 스레드가
  제어기 응답을 기다리며 도는 시간) 실행 내내 그대로다. 물리 스레드의 코어에서 다른 프로세스를 모두 빼도(`container_run.reserve`)
  없어지지 않았다. 원인은 찾지 못했고, 그런 실행은 버리고 새로 돌린다(`lane.sh`). PRO6000에서는 보지 못한 현상이다.

## 데이터에서 읽은 것

- 34 에피소드, 15 Hz, 한 에피소드에 박스 3개. 값은 pelvis 기준 좌/우 손바닥 포즈와 head yaw뿐이다.

  든 구간의 양손 간격 0.27~0.28 m.
- 집는 곳은 pelvis 기준 (0.43, −0.30) m, 놓는 곳은 (0.16, 0.39) m. 두 작업면의 높이는 같다.

  원점은 손바닥 접촉면이고 법선이 박스 축에서 왼손 12.3°, 오른손 34.3° 일정하게 어긋나 있다.
  (2026-11-23 밤: 이 어긋남에는 손 원점 오차가 섞여 있었고, 왼손은 손바닥 축 둘레로도 28° 돌아가 있었다.
  지금은 "기록 손 프레임 보정" 절의 보정을 쓴다. 예전 보정은 `--raw-hands`일 때만 적용된다.)

## 장면과 로봇 배치

- 벽·책상·바닥: UR5e 책상 장면을 물리 스키마 없이 배경으로 쓴다. 바닥과 벽은 방이 닫히도록 복제했다.
- 검은 IGRIS-C 운반 케이스(1.10 × 0.60 m 상판, 추정), 우체국 박스 3개, 롤테이너(0.92 × 0.70 × 1.70 m)와 갈색 박스 더미.
  물리 물체는 케이스·롤테이너·박스 3개, 모두 박스 충돌체다.
- 사용자 실측: 롤테이너에 쌓인 박스 윗면(적재면) **0.80 m**, 검은 케이스 윗면 **0.77 m**, 롤테이너 바깥 폭 **0.92 m**(안쪽 0.856 m).
  2026-11-23 밤까지는 두 면 모두 0.847 m였다(가장 낮은 박스에 닿기 쉽게 고른 값이었고 실제보다 4.7~7.7 cm 높았다).
  기록에서는 케이스가 적재면보다 평균 0.8 cm 낮게 보인다(34개 에피소드, 표준편차 1.9 cm). 실측 차이 3 cm와의 차는
  집는 쪽 손 목표에만 더한다(`prepare.height_profile`: 집는 곳에서 1, 놓는 곳에서 0인 가중으로 에피소드 7은 −2.7 cm).
- 로봇은 기록 기준 좌표계에서 (0.07, −0.03) m에 선다. 실측 높이와 손 보정을 넣은 뒤 네 자리를 시뮬로 비교했고
  이 자리가 가장 나았다("서는 위치 재확인" 절).
- 케이스 상판 크기, 롤테이너 깊이·높이(0.70 × 1.70 m), 갈색 박스 크기(41 × 31 × 20.9 cm, 세 단이 0.80 m가 되도록)와
  뒤쪽 줄 높이(두 단 더)는 영상을 보고 정한 추정값이다. 받침이 박스 주변 어디에 서는지도 추정이다(아래 절).

## RCV hand

[`hand_pose.json`](hand_pose.json)에 실기 목표값과 시뮬 관절각을 함께 둔다.

| 관절 | 왼손 실기 [°] | 오른손 실기 [°] | 시뮬 URDF 각 |
|---|---|---|---|
| MCP | 325.8984 | 170.0684 | 18° |
| Thumb CMC | 321.7676 | 111.3574 | −50° |
| Thumb IP | 248.2031 | 170.9473 | −45° |

- 실기 엔코더 영점은 어느 코드에도 없고, 주신 값은 이전 기본 자세와 달라 재조립된 것으로 보인다.
  그래서 실기 값을 각도로 직접 바꾸지 않고, 시뮬 자세를 좌우 대칭인 "약간 굽힘"으로 정한 뒤
  실기 값을 그 자세의 실기 목표로 기록했다(차이가 영점 오프셋). 엄지 두 관절의 부호는 실기에서 확인하지 않았다.
- MCP 18°는 손끝이 손바닥 면과 같은 평면에 오는 각이다. 제조사 고정 손은 MCP 10°, CMC −60°, IP −60°가 들어간 자세였다.
- 손은 재생 중 고정 자세다. 제조사 모델과 다른 점은 손 메시 위치, 손 마찰 0.6, 질량 없는 접촉 평판 하나뿐이다
  (`model/hands.json`에 기록, 질량·관성·관절·구동기는 그대로).

## 알아둘 한계

- **골반 보정은 시뮬 실측을 쓴다.** 이 시뮬에서는 발이 바닥에서 미끄러지고(분당 간격 20 cm, 방향 10°)
  골반이 발 위에서 최대 10 cm·6° 흔들린다. 박스를 9 cm 넘게 어긋나게 놓으면 넘어지므로 기본값(`--anchor pelvis`)은
  측정한 골반 자세로 목표를 방에 고정한다. 실기에는 이 측정이 없다. `--anchor none`이 보정 없는 pelvis 기준 재생이다.
- 손 접촉은 평판 하나와 비틀림 마찰로 근사했다. 실제 손의 MCP 순응과 DIP 스프링은 넣지 않았다.
- 박스 질량 0.3 kg(빈 박스 가정), 마찰 0.6은 가정값이다.
- 데이터 포즈를 그대로 쓰지 않는다: 손별 상수 회전 보정, 든 구간의 양손 쌍 명령, 집을 때·놓을 때 수평 맞춤,
  박스 중간 높이로의 수직 보정, 접근 시 한쪽 3 cm 더 벌림. 값은 출력의 `retarget.json`에 남는다.
- 로봇 상체 자기충돌과 팔–롤테이너 간섭은 IK에서 검사하지 않는다(물리에서는 로봇 충돌체가 장면과 부딪친다).
- 관절 유격 보정은 시뮬 실측 유격 각을, 받침면 여유는 장면의 면 위치를 쓴다. 둘 다 실기에는 따로 구해야 하는 정보다.
- heading 모드를 켜도 발은 미끄러진다. 발을 다시 디뎌 되돌릴 뿐이고, 그때 골반이 14~29 cm 움직인다.
- 포즈 스트림 모드(`--stream`)의 실행기는 받은 포즈만 쓰지만, 그 포즈를 방에 고정하는 골반 보정은 여전히 시뮬 실측이다.
  빼면(`--anchor none`) 3단 적재가 1/6이다. 실기에서는 정책의 시각이나 조종자가 그 몫을 해야 한다.
- 대역 행동모델(`pose_policy.py`)은 영상을 보지 않고, 시험 때 보류 에피소드의 라벨 이력을 관측으로 받는다. 망 출력의
  오차·묶음 경계·지연만 흉내 내며, 실제 정책이 박스를 잘못 찾는 경우는 다루지 않는다.
- 에피소드 8과 12는 세 번째 박스를 놓는 높이가 다른 에피소드와 달라 장면 추정이 맞지 않을 수 있다.
- 상대 EE ACT(`act_ee.py`)는 시뮬 영상으로만 학습·평가했다. 그림은 MuJoCo 렌더(로봇 단색, 배경 없음)이고 실제 카메라의
  화각·왜곡·노출과 맞춘 것이 아니다. 학습 데이터의 라벨에는 시뮬의 골반 실측이 들어간다(실행에는 쓰지 않는다).
